# TV official song / music-video switch

The full-screen TV player has a focusable **Switch to music video** / **Switch to song only** action. D-pad OK starts one request. Its label continues to describe the committed recording while a progress indicator is visible. Repeated OK during that request is ignored; unavailable, unsupported and failed requests have separate feedback and can be retried. Existing player Back/footer behavior remains in place. English and Portuguese strings are supplied; other locales use the English fallback.

The pairing comes from YouTube Music's explicit queue `counterpart` link. Discovery matches the requested ID against either side of that pair and accepts only an official music video (`MUSIC_VIDEO_TYPE_OMV`) paired with a song (`MUSIC_VIDEO_TYPE_ATV`). The first queue row, title, artist, artwork and search results are never used to guess a pair. A response without an exact link leaves playback unchanged. YouTube can omit these links, including for signed-out sessions.

Android prepares a separate paused ExoPlayer with an explicit source mode. A video request constructs merged video/audio sources; a song request constructs audio alone. This overrides the source for that queue item without writing the global watch-video preference. The backend waits at most 20 seconds for readiness, requires selected audio tracks, and checks that selected video tracks match the requested mode. Lookup is bounded to 15 seconds. Cast, live and offline switching are unsupported. An offline audio fallback cannot satisfy video confirmation.

Until preparation succeeds, the current player remains owned and playable. Preparation failure or cancellation before commit releases only the candidate. An incoming crossfade is first committed as the current owner, because it is already the recording shown by the player. Before switching, Android checks the exact item instance, queue index, playback revision, full queue identity/order, exact shuffle order, shuffle/repeat settings, local playback and live status. A track or queue change invalidates the prepared source. Leaving and returning to the same recording also invalidates the request. Account changes cancel pending discovery/preparation.

The confirmed operation replaces one visible queue slot and its backend item. It keeps every other queue entry and the existing shuffle permutation and repeat mode. It samples the latest position and playback intent immediately before committing, so pause/seek commands during preparation remain authoritative. Elapsed milliseconds are clamped to a known positive target duration; this preserves elapsed time, not musical or scene alignment between recordings with different introductions. Incompatible in-memory precache players are cancelled and released; persistent downloads and media cache are retained.

A rendition change refreshes now-playing metadata without using an ordinary track-transition event. It does not increment the listen count, restart Last.fm tracking, record the outgoing recording as a completed listen, or request endless-radio queue extension merely because its rendition changed. Other backends default to unsupported, and mobile screens retain their existing controls and preference behavior.

Source readiness and selected tracks are runtime checks. They do not establish that a Philips TV rendered the expected clip, that synchronization sounds correct, or that a remote sequence passed physical acceptance. Hardware switching in both directions, pause/seek while pending, shuffle/repeat behavior, unavailable links, failure recovery, Cast/live/offline refusal and navigation remain part of the controller's device validation.

## Verification

On Windows with Android Studio JBR and headless AWT, the final candidate passed 38 domain JVM tests, 3 exact-counterpart tests, 15 Media3 unit tests, 70 TV JVM tests with no failures/skips, and TV/mobile debug Kotlin compilation. The TV suite exercises the production action's D-pad activation, duplicate OK suppression while pending, focus retention, failure retry, committed label and directional exit. Domain tests cover identity/revision, queue/shuffle/repeat guards, duration clamp and explicit source-intent cache compatibility. These are policy/UI tests and compilation evidence; they do not execute actual ExoPlayer switching.

Full suites were also run without exclusions. The data suite exposed an unchanged browser-cookie test expecting a different synthetic cookie order; the Compose suite retained the existing Windows local-file `NetworkFirstInterceptorTest` failure. Those unrelated tests were neither changed nor weakened.
